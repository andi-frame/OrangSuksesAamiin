# Problem 3 — Autentikasi dan kepercayaan antar-service (Orang 2; sisi mock: Orang 1)

> Draf bagian laporan. Bukti: `make demo-mock-auth` (`docs/evidence/p3/mock-auth.log`), `make demo-p3`
> (`docs/evidence/p3/latest.log`), `make secrets`, dan test di `services/client-api` serta `services/auth-service`.

## 1. Rancangan solusi dan mekanisme

Prinsip: **tiap domain kepercayaan punya kredensial sendiri, diterbitkan dan divalidasi oleh pemiliknya, dan tidak ada
satu rahasia pun yang dipakai di dua domain.** Ada lima domain; tiap baris di bawah dibuktikan terpisah.

| Domain | Kredensial | Divalidasi oleh | Dipegang oleh | Bocor → dampak |
|---|---|---|---|---|
| BMKG | `X-BMKG-Key` (kunci opak) | bmkg-mock | bmkg-mock, Aggregator | hanya BMKG |
| PVMBG | `Authorization: Bearer pvmbg.v1.<klaim>.<HMAC>` (struktur lain) | pvmbg-mock | pvmbg-mock (rahasia penanda tangan), Aggregator (hanya token, tidak bisa mencetak token) | hanya PVMBG |
| API internal Aggregator | `X-Service-Key` | Aggregator | Aggregator, Client-Facing API | jalur internal; tidak membuka BMKG/PVMBG/klien |
| Operator mock | `X-Admin-Token` (satu per mock) | masing-masing mock | operator demo | `/admin/*` mock itu saja |
| Client downstream | `client_id` + `client_secret` per peran → JWT | Auth Service (penerbit) / Client-Facing API (pemeriksa) | masing-masing klien | hanya peran klien itu |

### Client downstream (Media, Tim Lapangan, BNPB Pusat)

- **Tiga identitas yang benar-benar berbeda** (`AUTH_MEDIA_*`, `AUTH_LAPANGAN_*`, `AUTH_PUSAT_*`: id dan secret masing-masing),
  bukan satu akun dengan bendera peran di sisi klien. Peran ditentukan Auth Service dari identitas yang lolos login
  dan ditulis ke klaim `role` **di dalam token bertanda tangan**; klien tidak dapat memilih perannya.
- **Access token**: JWT HS256, klaim `sub`, `role`, `jti`, `iat`, `exp`. TTL **60 detik** (`AUTH_ACCESS_TTL_SEC`, dapat diubah).
- **Refresh token**: 256 bit acak, **tidak pernah disimpan polos**: hanya hash SHA-256 di SQLite milik Auth Service
  (jaringan `auth-net` yang internal; hanya Auth Service yang menyentuhnya). Sekali pakai (rotate): `POST /v1/refresh` menandai
  yang lama `revoked` dalam transaksi yang sama dengan pembacaannya, lalu menerbitkan pasangan baru. TTL `AUTH_REFRESH_TTL_SEC` (24 jam).
- **Penegakan di sisi BNPB, per permintaan** (`services/client-api`):
  1. tanpa `Authorization: Bearer` → **401**; token rusak/kedaluwarsa/salah tanda tangan/peran tak dikenal → **403**;
  2. **Media** menerima **hanya field Ringkasan** lewat *whitelist* (`policy.FilterItem`): field baru yang kelak muncul di
     HazardEvent tidak bocor ke Media secara otomatis;
  3. permintaan eksplisit Media atas field Mentah (`fields=latitude`, `include=mentah`, …) **ditolak 403**. Aturannya
     whitelist juga (`policy.CheckQuery`): setiap nilai `fields` harus field Ringkasan dan `include` hanya boleh kosong/`summary`.
     Variasi penulisan (huruf besar, spasi, `fields[]`, parameter berulang, daftar dipisah koma, nama yang tak dikenal) tidak lolos;
  4. `/v1/sources/status` hanya untuk Lapangan dan Pusat (Media 403).
- Kredensial, kunci penanda tangan, dan konfigurasi dibaca dari environment (`obs.MustEnv`: service berhenti dengan pesan
  jelas bila kosong); repositori hanya memuat `.env.example` dengan nilai contoh.

```mermaid
sequenceDiagram
  participant C as Klien (Lapangan)
  participant A as Auth Service
  participant API as Client-Facing API
  participant G as Aggregator
  C->>A: POST /v1/token {client_id, client_secret}
  A-->>C: access JWT (60 s, role) + refresh (opaque)
  C->>API: GET /v1/hazards  Bearer access
  API->>API: verifikasi tanda tangan, exp, peran; terapkan kebijakan field
  API->>G: GET /internal/hazards  X-Service-Key
  API-->>C: 200 (Ringkasan atau penuh)
  Note over C,API: setelah 60 s: 403 (token kedaluwarsa)
  C->>A: POST /v1/refresh {refresh}
  A-->>C: pasangan baru; refresh lama tidak berlaku lagi
```

## 2. Alasan keputusan dan trade-off

| Alternatif | Mengapa tidak dipilih |
|---|---|
| **Satu kunci untuk semua** (kondisi awal Astolfo) | persis masalah di soal: kunci Media bocor → data mentah bocor, dan kunci BMKG menembus PVMBG |
| **API key statis per klien** (tanpa token) | tidak ada kedaluwarsa/refresh, sedangkan Lapangan wajib ber-TTL pendek; kunci bocor berlaku selamanya |
| **Opaque token + introspeksi** ke Auth Service di tiap permintaan | pencabutan seketika, tetapi setiap permintaan klien menambah satu panggilan jaringan dan Auth Service menjadi titik gagal bagi jalur baca (bertentangan dengan tujuan P2) |
| **JWT asimetris (RS256/EdDSA)** | Client-Facing API cukup memegang kunci publik, jadi kompromi API tidak bisa mencetak token. Lebih baik secara keamanan, tetapi menambah pengelolaan kunci; **dicatat sebagai perbaikan M2** |
| **OAuth2/Keycloak penuh** | berlebihan untuk tiga klien read-only; sulit didemokan dengan TTL 60 s dan sulit ditelusuri ke kode sendiri |
| **JWT HS256 + refresh opaque** ✔ | verifikasi lokal (jalur baca tidak bergantung pada Auth Service), TTL pendek, refresh dapat dicabut per token; sederhana dan mudah dibuktikan |

Trade-off yang diterima: `AUTH_JWT_SECRET` dipegang **dua** service milik BNPB (Auth Service dan Client-Facing API). Rahasia
ini independen dari kredensial BMKG, PVMBG, kunci layanan, dan token admin, sehingga kompromi tidak merambat ke domain lain.
Konsekuensinya, kompromi Client-Facing API cukup untuk mencetak token klien. Itulah alasan pilihan asimetris dicatat sebagai
langkah berikutnya.

## 3. Batasan yang disadari

- **Access token lama tidak dicabut seketika saat refresh**: JWT bersifat stateless, jadi token yang belum kedaluwarsa tetap
  berlaku sampai `exp` (maksimum 60 detik). Yang dicabut seketika adalah *refresh token* lama (terbukti: dipakai ulang → 403).
  Pencabutan seketika menuntut introspeksi atau daftar `jti` terbarukan (lihat alternatif di atas).
- **Tidak ada deteksi pemakaian ulang refresh token** (keluarga token tidak dicabut ketika refresh yang sudah terpakai muncul lagi).
- **`/v1/token` tidak dibatasi percobaan** (tanpa lockout/rate limit per klien). Perbandingan secret memakai waktu-konstan.
- **Pembatas laju Client-Facing API bersifat global** (satu token bucket), bukan per klien, dan dipasang sebelum autentikasi;
  banjir permintaan tanpa token ikut menghabiskan jatah. Dipilih karena sederhana dan cukup untuk P2; per-klien setelah
  autentikasi adalah perbaikan M2.
- Token kedaluwarsa dijawab **403** (bukan 401) mengikuti kontrak yang dibekukan di `docs/contracts.md`.
- Tanpa TLS di dalam jaringan Compose (asumsi jaringan tepercaya/ingress TLS di produksi); secret klien statis di environment
  tanpa perkakas rotasi; SQLite Auth Service berinstance tunggal (M2 membutuhkan penyimpanan bersama).

## 5. Jawaban butir "Di laporan"

**Mekanisme yang dipakai.** Dua lapis. (1) Antar-instansi: kredensial BMKG (kunci opak) dan PVMBG (token bertanda tangan HMAC
berstruktur lain, rahasia penanda tangan hanya di mock PVMBG) saling asing, masing-masing divalidasi oleh pemiliknya.
(2) Klien downstream: Auth Service menerbitkan JWT HS256 ber-TTL 60 detik per peran ditambah refresh token opaque sekali
pakai; Client-Facing API memeriksa setiap permintaan dan menegakkan klasifikasi Ringkasan/Mentah di server.

**Mengapa tidak membuka celah baru.**
- *Pemalsuan token*: algoritma dikunci ke HS256 (`alg=none` dan algoritma lain ditolak; diuji), `exp` wajib ada dan diperiksa
  (token bertanda tangan tanpa `exp` ditolak; diuji), peran harus salah satu dari tiga nilai yang dikenal.
- *Eskalasi peran dari sisi klien*: peran hanya berasal dari klaim bertanda tangan; header atau parameter buatan klien
  (mis. `X-Role`) tidak dibaca. Media tidak punya jalur apa pun ke field Mentah karena respons dibentuk dengan whitelist,
  bukan dengan menghapus field yang dikenal.
- *Kebocoran lintas domain*: rahasia tiap domain terpisah dan tidak dipakai ulang; Aggregator memegang token PVMBG tetapi
  tidak rahasia penanda tangannya, sehingga tidak dapat mencetak atau mengadministrasi PVMBG (diverifikasi `demo-mock-auth`).
- *Pencurian dari penyimpanan*: refresh token hanya tersimpan sebagai hash; basis data Auth berada di jaringan internal yang
  tidak dapat dijangkau service lain. Pencurian refresh token terbatas oleh sekali-pakai dan TTL.
- *Jendela penyalahgunaan*: token curian berguna paling lama 60 detik (access) atau sekali (refresh).
- *Pembatasan yang diakui* ada di §3 (tidak ada pencabutan access token seketika; HS256 dibagi dua service BNPB).
