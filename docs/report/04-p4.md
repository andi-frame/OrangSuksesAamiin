## 1. Rancangan solusi dan mekanisme

BNPB dipisah menurut tanggung jawab dan data yang dimiliki. **Aggregator** mengambil data BMKG/PVMBG, memetakan
`HazardEvent`, memiliki Canonical Store, dan menyediakan API baca internal. **Client-Facing API** memeriksa token,
menerapkan hak akses, lalu meminta data dari API Aggregator melalui jaringan. **Auth Service** menerbitkan dan
memperbarui token klien dengan penyimpanan refresh miliknya sendiri. **Kafka** menyalurkan event; consumer dashboard
dan notifier berjalan di container dan consumer group masing-masing. Kedua mock sumber juga berjalan sendiri.

Pemecahan ini mengikuti batas perubahan dan kegagalan. Perubahan autentikasi tidak menuntut Aggregator dibangun
ulang; perubahan mapping tidak menuntut Client-Facing API dibangun ulang. Consumer tidak berada pada jalur polling
atau baca. Pemisahan berdasarkan jenis bencana akan menduplikasi autentikasi, API klien, dan kontrak kanonik;
karena itu Aggregator tetap satu pemilik format dan penyimpanan kanonik pada M1.

Setiap service Go memiliki Dockerfile sendiri. Compose menempatkan PostgreSQL hanya di `canonical-net` bersama
Aggregator, tanpa port database ke host. Client-Facing API hanya berada di `app-net` dan membaca lewat
`GET /internal/hazards` atau `GET /internal/hazards/{id}` dengan `X-Service-Key`. Kafka dan para consumer berada
di `broker-net`; broker tidak menjadi jalur akses ke Canonical Store. Jaringan ini menegakkan kepemilikan storage
secara operasional, selain pemisahan modul dalam kode.

Penyimpanan memakai **PostgreSQL 16 dengan `attributes JSONB`**. Identitas, tipe, severity, lokasi, waktu, dan
versi adalah kolom tetap yang dapat diindeks. Atribut khusus sumber dan field baru, termasuk
`confidence_level`, menjadi properti dokumen JSONB. Saat PVMBG menambah field, Aggregator menulis dokumen baru
tanpa `ALTER TABLE`; record lama dan baru tetap dapat dibaca melalui API yang sama. Tabel `outbox` berada di
database milik Aggregator agar perubahan hazard dan pesan yang akan diterbitkan dapat disimpan dalam satu
transaksi. Pembuatan tabel `CREATE TABLE IF NOT EXISTS` pada saat awal service hidup bukan migrasi untuk tiap
perubahan skema sumber.

## 2. Alasan keputusan dan trade-off

| Pilihan penyimpanan | Kelebihan | Konsekuensi untuk M1 |
|---|---|---|
| **PostgreSQL + JSONB (dipilih)** | Atribut dinamis tanpa migrasi, query terindeks untuk field kanonik, transaksi hazard + outbox dalam satu database | Perlu menjalankan PostgreSQL; field di dalam JSONB tidak memiliki validasi skema database otomatis; satu instance database pada M1 |
| Document store, misalnya MongoDB | Dokumen dinamis adalah model alami; mudah menampung field sumber baru | Transaksi dan outbox lintas koleksi menambah konfigurasi dan beban operasional; kelompok tetap memerlukan query terstruktur atas field kanonik |
| Key-value store, misalnya Redis | Sederhana untuk baca berdasarkan `hazard_id` dan menerima dokumen baru | Filtering, pagination, persistensi, dan transaksi hazard + outbox memerlukan rancangan tambahan; tidak cocok sebagai satu-satunya canonical store untuk query M1 |
| Tabel relasional dengan kolom tetap untuk setiap atribut | Validasi dan indeks SQL langsung untuk semua field | Field PVMBG baru membutuhkan DDL/migrasi, tepat coupling yang dipersoalkan P4 |

JSONB dipilih karena memisahkan bagian kontrak yang stabil dari atribut yang berubah, sambil mempertahankan
transaksi relasional. Batas service mengikuti kepemilikan data dan fungsi yang dapat dirilis sendiri, bukan
sekadar membagi satu proses menjadi beberapa container yang masih berbagi database.

## 3. Batasan yang disadari

- Satu Aggregator dan satu PostgreSQL dipakai pada M1. Demo membuktikan deploy service independen, bukan
  ketersediaan tinggi database atau rolling upgrade beberapa replika.
- `attributes JSONB` menjaga bentuk nilai JSON, tetapi makna dan tipe field tambahan tidak divalidasi oleh
  PostgreSQL. Mapper Aggregator tetap memvalidasi field kanonik wajib (lihat P1).
- Database tidak dipublikasikan ke host aplikasi dan hanya terhubung ke `canonical-net`. Operator demo dapat
  memeriksa isi database lewat `docker compose exec`; itu akses administrasi untuk bukti, bukan jalur akses service.
- Saat PVMBG dibangun ulang, data vulkanik terbaru tidak bertambah sampai polling pulih. Data seismik dan
  record lama tetap tersedia dari Canonical Store; penanda kebaruan dijelaskan pada P2.

## 5. Jawaban

**Mengapa batas service tersebut:** Aggregator memiliki fakta kanonik dan seluruh penulisan; Client-Facing API
memiliki kebijakan akses; Auth Service memiliki siklus token; consumer memiliki pemrosesan event. Pemisahan
tersebut memungkinkan satu bagian dibangun ulang saat bagian yang tidak bergantung padanya tetap melayani.
Alternatif pembagian berdasarkan sumber bencana akan menduplikasi API, autentikasi, dan penyimpanan kanonik.

**Mengapa storage tersebut:** PostgreSQL dengan JSONB menerima atribut dinamis tanpa migrasi dan dapat menyimpan
hazard bersama outbox secara atomik. Document store dan key-value store juga dapat menerima atribut baru,
tetapi menambah kerja untuk transaksi, query, atau pagination yang dibutuhkan sistem ini (§2).
