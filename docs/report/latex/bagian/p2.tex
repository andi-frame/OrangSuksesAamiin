\chapter{Problem 2 -- Concurrency, Availability, dan Graceful Degradation}

\begin{ringkas}
Gateway tidak memanggil BMKG atau PVMBG saat melayani klien. Polling dijalankan di \textbf{putaran terpisah per sumber}
dan hasilnya disimpan di Canonical Store. Klien hanya membaca dari store, jadi PVMBG yang lambat atau mati tidak bisa
menahan permintaan lain. Lonjakan beban ditolak seketika dengan HTTP~429, dan saat PVMBG mati data vulkanik terakhir
tetap tersaji dengan penanda \code{stale}.
\end{ringkas}

\section{Rancangan solusi dan mekanisme}

\textbf{Pokok idenya: pisahkan \emph{mengambil data} dari \emph{melayani klien}.} Prototipe Astolfo memanggil BMKG lalu
PVMBG secara berurutan di dalam satu permintaan klien, sehingga lambatnya PVMBG dirasakan semua orang. Pada rancangan
kami, jalur layanan tidak pernah menyentuh sumber.

\input{bagian/fig-p2}

\begin{enumerate}
 \item \textbf{Satu putaran polling per sumber} (\code{poller/loop.go}). BMKG dan PVMBG masing-masing punya goroutine sendiri dengan timeout permintaan (\code{SOURCE_TIMEOUT_SEC}), timeout siklus, dan \emph{circuit breaker} (\code{resilience/breaker.go}). Breaker membuka setelah beberapa kegagalan beruntun, lalu mengirim satu percobaan (\emph{half-open}) setelah \code{BREAKER_OPEN_SEC}. Siklus berikutnya baru mulai \code{POLL_INTERVAL_SEC} setelah siklus sebelumnya selesai, jadi sumber yang lambat tidak pernah menerima permintaan bertumpuk.
 \item \textbf{Jalur layanan tidak memanggil BMKG atau PVMBG sama sekali.} Client-Facing API membaca \cmd{GET /internal/*} milik Aggregator, yang membaca Canonical Store. Setiap permintaan klien dilayani goroutine \code{net/http}-nya sendiri, sehingga permintaan data BMKG tidak berbagi antrean atau kunci dengan apa pun yang menunggu PVMBG.
 \item \textbf{Pembatas laju (token bucket)} di Client-Facing API (\code{CLIENT_RATE_LIMIT_RPS} dan \code{CLIENT_RATE_LIMIT_BURST}, bawaan 500 dan 1000). Kelebihan beban \emph{ditolak seketika} dengan \code{429} dan \code{Retry-After}, tidak diantre. \code{/health} dan \code{/ready} dikecualikan supaya pemeriksaan kesehatan tetap menjawab saat beban tinggi.
 \item \textbf{Degradasi terkendali.} Aggregator menyimpan \code{freshness} untuk tiap sumber (\code{state}, \code{last_success_at}, \code{stale_since}). Saat PVMBG mati, data vulkanik terakhir tetap disajikan dari store. Client-Facing API menandai tiap item \cmd{stale: true} dan meneruskan \code{freshness.PVMBG.stale_since}. Tidak ada jalur yang mengubah matinya satu sumber menjadi galat 500 atau permintaan yang menggantung.
\end{enumerate}

\textbf{Harga yang diterima.} Data yang dilayani \emph{selalu} berasal dari store, jadi kesegarannya setara interval
polling (3~detik). Selain itu, kebijakan laju bersifat global (lihat bagian berikut).

\section{Batasan yang disadari}

\begin{itemize}
 \item \textbf{Pembatas laju bersifat global}, bukan per klien, dan dipasang \emph{sebelum} autentikasi. Satu klien agresif atau banjir permintaan tanpa token dapat menghabiskan jatah klien lain. Ini cukup untuk membuktikan perlindungan sumber daya pada M1; pembatasan per klien adalah perbaikan untuk M2.
 \item \textbf{Tidak ada batas jumlah koneksi bersamaan} selain laju. Beban koneksi lambat (\emph{slowloris}) hanya dibatasi \code{ReadHeaderTimeout} 5~detik.
 \item \textbf{Satu instance} Client-Facing API dan Aggregator. Skala horizontal (termasuk pembatas laju terdistribusi) masuk M2.
 \item Penanda \code{stale} pada permintaan satu hazard membutuhkan satu panggilan tambahan ke \code{/internal/sources/status}.
 \item Data saat outage adalah potret terakhir; tidak ada estimasi atau ekstrapolasi.
 \item Hasil load test berasal dari \textbf{satu mesin} (k6, Docker, dan semua service berbagi CPU mesin Windows~11). Angka absolutnya bukan klaim kapasitas produksi. Throughput sustained dibatasi \emph{think time} 0,1~detik per VU (sekitar 450 permintaan per detik untuk 50 VU), bukan oleh server.
\end{itemize}

\textbf{Catatan tentang overload.} Dalam 20~detik, token bucket dengan 500 token per detik dan \emph{burst} 1000 secara
teori meloloskan sekitar $500\times 20+1000 \approx 11.000$ permintaan. Hasil ukur 10.989 permintaan sukses sangat
dekat dengan angka itu, artinya pembatas bekerja sesuai konfigurasi, dan semua sisanya ditolak dengan 429 tanpa satu pun 5xx.

\section{Jawaban butir ``Di laporan''}

\begin{jawaban}
\textbf{Model konkurensi.} Putaran polling terpisah per sumber (dengan timeout dan circuit breaker) yang menulis ke
Canonical Store. Jalur layanan hanya membaca store lewat API Aggregator, dengan token bucket di depannya. Pemetaan ke
tiga kegagalan ada di bagian~\ref{sec:p2-tiga}.

\textbf{Konfigurasi dan tooling load test.} k6; 50 VU selama 60~detik (sustained) dan 150 VU selama 20~detik (overload);
respons diklasifikasi 200/429/tak tertangani; ambang \texttt{unhandled < 1\%} dan \texttt{p95 < 300 ms}. Rinciannya di
bagian~\ref{sec:p2-load}.
\end{jawaban}
